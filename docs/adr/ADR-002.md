# ADR-002: MySQL en vez de PostgreSQL, y despliegue nativo en vez de Docker para el prototipo

## Estado

Aceptado — 2026-07-27

## Contexto

`ADR-001` fijó PostgreSQL como base de datos y Docker en todos los entornos como estrategia de despliegue. Esa fue la decisión "ideal" tomada al fundar el proyecto, sin conocer todavía el entorno real disponible para construir. Antes de empezar la Fase 2 (prototipo funcional del piloto, sprint de 30 días, no producción — ver `docs/estado-actual.md`), se verificó ese entorno real:

- El desarrollador trabaja **solo**, sin equipo técnico, con 30 días de tiempo disponible para entregar un prototipo confiable y funcional, no un sistema en producción.
- Su entorno local es **Laragon (Windows)**, con **PHP 8.1.10, Composer, Node 22, MySQL 8.0.30 y Redis** ya instalados y funcionando. No tiene PostgreSQL instalado, y agregarlo — junto con Docker Desktop para replicar la topología completa de contenedores en Windows — introduce fricción de instalación y aprendizaje que no aporta nada medible a un prototipo de 30 días.
- Su servidor de pruebas es un **Droplet de DigitalOcean**, que decidió configurar con **OpenLiteSpeed + MySQL de forma nativa**, sin contenedores, priorizando explícitamente la simplicidad de operar él solo una pila que está aprendiendo, sobre la portabilidad teórica que ofrece Docker.
- El resto de las decisiones de `ADR-001` (Laravel + Next.js, monolito modular por dominio, multi-tenant desde el modelo de datos con `tenant_id`, servidores stateless, trabajo pesado por colas) no cambia — solo la base de datos y la estrategia de despliegue.

## Decisión

Se reemplaza **PostgreSQL por MySQL 8** como motor de base de datos en todos los entornos (local y droplet de pruebas), y se reemplaza **Docker como estrategia de despliegue obligatoria por despliegue nativo**: entorno local con Laragon (PHP, MySQL, Redis y Node corriendo directamente sobre Windows), y servidor de pruebas con OpenLiteSpeed + PHP + MySQL + Redis instalados nativamente sobre el droplet, sin contenedores. El despliegue consiste en `git pull` + `composer install --no-dev` + `npm run build` + `artisan migrate` ejecutado directamente en el servidor. Redis se mantiene sin cambios como cache y backend de colas. Contenerizar queda como opción a evaluar más adelante, no descartada para siempre, si el proyecto avanza a una fase de producción real con más de un servidor (Fase 5 del roadmap, SaaS).

## Alternativas consideradas

- **Mantener PostgreSQL + Docker tal como lo fijó `ADR-001`:** descartado para esta fase. Exige instalar y aprender PostgreSQL (motor no disponible en el entorno local actual) y Docker Desktop en Windows (con su capa adicional de virtualización, WSL2, y la complejidad de mantener Compose sincronizado entre entornos) al mismo tiempo que se construye el prototipo, en un sprint de 30 días con un solo desarrollador. Ese costo de aprendizaje y fricción de instalación no tiene contrapartida medible hoy: el prototipo no tiene tráfico real, no tiene múltiples servidores que orquestar, y ninguna de las capacidades diferenciales de PostgreSQL o de Docker (particionamiento nativo, portabilidad multi-cloud, aislamiento de contenedores) se necesita todavía para validar el piloto.
- **MySQL local + Docker en el droplet (híbrido):** descartado por inconsistencia entre entornos — reintroduce exactamente el riesgo de "funciona en mi máquina, no en el servidor" que la topología uniforme buscaba evitar, sin resolver la fricción de aprender Docker.
- **PostgreSQL nativo en ambos entornos (sin Docker, pero manteniendo el motor original):** descartado porque igual exige instalar y operar un motor no disponible en Laragon hoy, sin el beneficio de mantener Docker como capa de portabilidad; si de todas formas se abandona Docker, no hay razón para pagar el costo de instalar PostgreSQL en vez de usar el MySQL ya instalado y funcionando.
- **MySQL + despliegue nativo (la decisión tomada):** es la única combinación que aprovecha software ya instalado y funcionando en ambos entornos (MySQL en Laragon, capacidad de instalar MySQL nativo en el droplet), minimiza el número de piezas nuevas que un desarrollador solo debe aprender en 30 días, y no cierra la puerta a Docker ni a PostgreSQL más adelante si una fase de producción real lo justifica.

## Consecuencias

**Se gana:**
- Velocidad de arranque: el entorno local ya funciona hoy (Laragon con MySQL, Redis, PHP y Node instalados), sin instalar ni configurar un motor de base de datos ni una capa de contenedores nueva.
- Menos partes móviles que aprender en solitario: un desarrollador sin equipo, en un sprint de 30 días, reduce su superficie de aprendizaje a OpenLiteSpeed y despliegue por SSH, en vez de sumar también PostgreSQL y Docker/Compose al mismo tiempo.
- Un despliegue más fácil de depurar cuando algo falla: los procesos corren directamente sobre el sistema operativo del droplet, visibles con las herramientas estándar del propio servidor, sin una capa de contenedores adicional que inspeccionar.
- Todas las decisiones estructurales de `ADR-001` que sí importan para el prototipo (monolito modular, `tenant_id` desde el día uno, stateless, colas) permanecen intactas — este ADR no las reabre.

**Se sacrifica (de forma consciente, no permanente):**
- La portabilidad multi-cloud fácil que ofrece Docker: mover el sistema a otro proveedor o a múltiples servidores hoy exigiría replicar manualmente la configuración nativa del droplet, en vez de simplemente correr la misma imagen en otro lado. Aceptable porque el prototipo corre en un solo servidor y no tiene ese requisito todavía.
- Algunas capacidades nativas de PostgreSQL que no se necesitan en esta etapa: `JSONB` más maduro (indexación y operadores más ricos que el tipo `JSON` de MySQL 8, aunque MySQL 8 sí soporta índices funcionales/generados sobre campos JSON), y particionamiento nativo más fino. Ninguna de las dos es un requisito del prototipo de 30 días; se reevalúan si el volumen de datos o la necesidad de atributos de esquema variable lo justifican más adelante.
- El aislamiento de fallos y de despliegue por contenedor que ofrecía Docker Compose en local: un desarrollador debe cuidar más manualmente que su entorno local no diverja del servidor, aunque ambos ahora comparten la misma base tecnológica (MySQL, PHP nativo), lo que reduce ese riesgo respecto a tener motores distintos.

**Queda pendiente** (revisar en Fase 5 del roadmap, si el proyecto avanza a SaaS con más de un servidor):
- Si contenerizar (Docker u otra herramienta) aporta valor medible una vez exista más de un servidor de aplicación o un equipo más grande que deba reproducir el mismo entorno.
- Si el tipo `JSON` de MySQL 8 se vuelve insuficiente para algún caso de atributos de producto muy variables, evaluar entonces si migrar esa tabla específica a un motor distinto se justifica.
- Automatizar el despliegue nativo actual (hoy manual o por script simple) vía GitHub Actions ejecutando el mismo script por SSH, sin necesitar Docker para lograrlo (ver `docs/development/ci-cd.md`).
