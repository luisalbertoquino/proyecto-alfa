# ADR-001: Stack tecnológico y arquitectura monolito-modular multi-tenant desde el modelo de datos

## Estado

Aceptado — 2026-07-27

## Contexto

Proyecto Alfa nace como la tienda virtual de un negocio real (el piloto), pero desde su concepción está pensado para evolucionar a una plataforma SaaS multi-tenant donde otros emprendedores creen sus propias tiendas sobre la misma base (ver `docs/business/vision-producto.md`). Había que elegir, antes de escribir el primer módulo de dominio, tanto el stack tecnológico como el patrón de arquitectura general, sabiendo que:

- El equipo es reducido en esta fase de fundación, sin capacidad operativa para administrar la complejidad de microservicios desde el día uno.
- El sistema debe centralizar capacidades de negocio hoy dispersas (catálogo, pedidos, inventario, envíos, proveedores, publicidad, analítica, canales, IA) sin que el acoplamiento entre ellas crezca sin control a medida que el equipo y el producto crecen.
- Postergar la decisión de multi-tenancy hasta que exista un segundo cliente obligaría a una migración de datos dolorosa y riesgosa sobre un sistema ya en producción con el negocio piloto operando.
- El sistema debe soportar tanto una tienda de cara al público con necesidades de conversión y SEO, como un panel administrativo interno, ambos consumiendo la misma fuente de datos.

## Decisión

Se adopta como stack tecnológico **Laravel** (API backend), **Next.js** (frontend de `apps/web` y `apps/admin`), **PostgreSQL** (base de datos), **Redis** (cache y colas), **Docker** (contenedores), **Cloudflare** (CDN/seguridad) y **GitHub Actions** (CI/CD). Sobre ese stack, se adopta una arquitectura de **monolito modular, API-first**, organizada en módulos de dominio con fronteras explícitas (`Catalogo`, `Pedidos`, `Inventario`, `Envios`, `Proveedores`, `Publicidad`, `Analitica`, `Canales`, `IA`), y **multi-tenant desde el modelo de datos**: toda tabla de negocio incluye `tenant_id` indexado desde su primera migración, aunque hoy exista un solo tenant en operación.

## Alternativas consideradas

- **Microservicios desde el inicio:** descartado por la complejidad operativa (orquestación, observabilidad distribuida, despliegue independiente) que un equipo reducido en fase de fundación no puede sostener; se opta por extraer un módulo a servicio independiente solo cuando exista una razón medible (carga, equipo dedicado, ciclo de despliegue distinto), no por adelantado.
- **Monolito no modular (organización por capa técnica, ej. `Controllers/`, `Models/` compartidos):** descartado porque, según la experiencia documentada en `docs/architecture/principios-de-arquitectura.md`, es la causa más común de que un sistema de comercio electrónico se vuelva lento de mantener a medida que crecen las funcionalidades — un cambio en un dominio termina rompiendo otro sin fronteras explícitas.
- **Multi-tenant diferido** (agregar `tenant_id` solo cuando exista un segundo cliente real): descartado porque migrar un esquema ya en producción, con el negocio piloto operando datos reales, a una estructura multi-tenant es significativamente más riesgoso y costoso que incluir `tenant_id` desde la primera migración, cuando el costo marginal es prácticamente nulo.
- **Otro stack backend/frontend** (ej. Node.js + Express, Django, Rails; u otro framework frontend): no se documenta una comparación exhaustiva en este ADR porque la decisión de stack ya estaba tomada al fundar el proyecto (ver `README.md` y `docs/architecture/vision-tecnica.md`); este ADR registra y formaliza esa decisión ya vigente, no la reabre. Una justificación detallada de cada tecnología queda pendiente en un documento de stack técnico dedicado (ver `vision-tecnica.md`).
- **Otra base de datos no relacional** (ej. MongoDB) para mayor flexibilidad de esquema: descartado porque el dominio del negocio (pedidos, inventario, transacciones) tiene relaciones e integridad que un modelo relacional garantiza de forma más directa, y PostgreSQL soporta bien tanto la carga transaccional como el aislamiento multi-tenant por `tenant_id` o, a futuro, por schema.

## Consecuencias

**Se gana:**
- Un solo despliegue y una sola base de código que un equipo reducido puede operar y razonar sobre ella completa.
- Capacidad de escalar horizontalmente sin reescritura (servidores stateless, sesión y cache en Redis) para soportar picos de tráfico y crecimiento de tenants.
- Ningún tenant nuevo requiere una migración de esquema — el segundo cliente del modelo SaaS se incorpora sin tocar la estructura de datos.
- Fronteras de módulo que permiten a un desarrollador nuevo predecir dónde está cada cosa, y que permiten extraer un módulo a servicio independiente el día que haya una razón medible para hacerlo (candidato más probable: `IA`, por su perfil de cómputo distinto).

**Se sacrifica:**
- No hay aislamiento de fallos ni de despliegue entre módulos mientras sigan dentro del mismo monolito: un incidente severo de infraestructura afecta a todos los módulos a la vez (mitigado a nivel de integración externa por el principio de "diseñado para reemplazar", no a nivel de infraestructura completa).
- Cada tabla de negocio paga el costo (mínimo, pero real) de una columna y un índice adicionales de `tenant_id` desde el primer día, incluso mientras solo existe un tenant.
- El equipo debe mantener disciplina activa (fronteras entre módulos, scope automático de tenant) para que las ventajas del monolito modular no se erosionen con el tiempo — a diferencia de microservicios, donde el aislamiento es forzado por la infraestructura misma.

**Queda pendiente** (ver `Decisiones futuras` de `docs/architecture/vision-tecnica.md`):
- El umbral de tráfico o número de tenants a partir del cual se evalúa aislar un tenant grande en su propio schema o base de datos dedicada.
- El punto exacto en el que un módulo se extrae a servicio independiente.
- La estrategia de versionado de API cuando exista más de un cliente externo real (integradores del modelo SaaS).
- La justificación detallada, tecnología por tecnología, del stack — pendiente como documento dedicado referenciado desde `vision-tecnica.md`.
